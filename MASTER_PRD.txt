This document is the single source of truth for this project.

Before making implementation decisions:
1. Read this entire PRD.

3. Inspect the available installed skills and use relevant ones.
4. Do not blindly rewrite existing code.

After completing each phase:

- Fix obvious issues.
- Check responsiveness.
- Check console errors.
- Check interactions.
- Only then proceed to the next phase.

Do not attempt to build all phases simultaneously.

1. PRODUCT OVERVIEW
================================================================================

Build a premium, immersive 3D portfolio website for a software developer /
full-stack developer.

The website should feel like a real personal digital environment, not a
conventional portfolio template.

The core experience should combine:

* Premium editorial portfolio design
* Immersive 3D / WebGL elements
* Smooth scroll-based storytelling
* Interactive project showcases
* Functional HTML project previews
* Developer-focused visual language
* Subtle motion and micro-interactions
* Strong typography and spacing
* Professional information hierarchy
* Responsive behavior across desktop, tablet, and mobile

The final result must feel human-designed, intentional, sophisticated, and
production-quality.

Avoid the visual characteristics commonly associated with generic
AI-generated websites ("AI slop"), including excessive gradients, random
glowing blobs, excessive glassmorphism, unnecessary rounded cards, excessive
animations, generic SaaS layouts, and meaningless decorative elements.

The website should prioritize art direction, usability, hierarchy, and
storytelling over adding effects simply because they are technically
possible.

6. 3D / IMMERSIVE VISUAL DIRECTION
================================================================================

Create a custom interactive 3D visual rather than using a generic 3D model
simply for decoration.

Possible concept: a floating digital workspace / abstract developer
environment consisting of:

* Floating browser windows
* Code fragments
* UI panels
* Small project cards
* Data nodes
* Subtle geometric structures
* Interactive cursor movement
* Depth layers
* Soft lighting

The 3D scene should communicate: Code → Build → Iterate → Ship
rather than simply being an abstract object.

Interaction ideas:
* Mouse movement subtly influences camera position
* Scroll changes the scene composition
* Project elements move slightly based on scroll depth
* Hovering over important objects reveals information
* Clicking a project object opens its project preview

Animations must be smooth and restrained.

Avoid:
* Constant spinning
* Excessive particle effects
* Giant glowing spheres
* Rainbow gradients
* Overly aggressive camera movement
* Effects that make the website difficult to use

The 3D layer must never compromise readability or performance.

REVISED — visual variety is required, not optional:
Current implementation only used two flat code-text panels ("engine.ts"
and a "LIFECYCLE PIPELINE" list), which reads as repetitive and visually
flat despite being technically "3D". Code fragments are only ONE of the
element types listed above — the scene must include at least one element
from a DIFFERENT category to create real visual variety, for example:
* A floating browser-window mockup showing an actual mini UI (buttons,
  cards, a small chart or layout) — not more code text — so the eye has
  something other than syntax-highlighted text to read.
* A small project card with a title/thumbnail-style treatment.
* A data-node/network element (connected dots/lines suggesting a system
  graph) purely as a visual/geometric element, not more text.
Do not build the Hero scene as "the same code-panel component, repeated
with different text" — vary the element TYPE, not just its content.

25. RESPONSIVE DESIGN
================================================================================

Desktop:
* Full immersive 3D experience
* Large typography
* Multi-column project layouts
* Advanced hover interactions

Tablet:
* Reduce 3D complexity
* Adapt grid
* Reduce typography scale

Mobile:
* Prioritize readability
* Simplify 3D
* Disable expensive effects when necessary
* Use touch-friendly interactions
* Keep project previews functional
* Maintain the same visual identity

The mobile version must not simply be a compressed desktop version.

================================================================================
26. PERFORMANCE REQUIREMENTS
================================================================================

The 3D experience must not unnecessarily destroy performance.

Requirements:
* Lazy-load heavy assets
* Optimize 3D models
* Avoid unnecessary render loops
* Use GPU-friendly effects
* Compress images
* Code-split where appropriate
* Lazy-load project previews
* Do not load every project demo simultaneously

Provide a graceful fallback if WebGL is unavailable. The portfolio must
remain usable even without advanced 3D rendering.

================================================================================
27. TECHNOLOGY DIRECTION
================================================================================

Use modern web technologies where appropriate.

Preferred architecture:
Frontend: React / Next.js
Styling: CSS / Tailwind where appropriate
3D: Three.js / React Three Fiber
Animation: GSAP / Framer Motion where appropriate
Icons: Lucide or another minimal icon system
Data: Local structured project data / JSON / TypeScript objects

Do not introduce a library merely because it is popular. Every dependency
should have a clear purpose.

If the existing project structure already uses a different stack, preserve
the existing architecture unless there is a strong technical reason to
change it.

Runtime & Deployment Clarification:

* Node.js and npm are development-time tools only (dev server, build
  process, package management). They are NOT part of what ships to the
  visitor's browser.
* This project does NOT require a backend server, database, or API routes.
  All content (personal info, skills, projects) is local structured data
  (JSON/TypeScript objects) as described in Section 28 — there is no
  dynamic server-side logic.
* Target deployment platforms are Vercel and/or Netlify via a connected
  Git repository (automatic build on push). Do not assume or require a
  custom Node.js server, a VPS, or manual server management.
* Prefer Next.js static export (`output: 'export'`) or an equivalent
  fully static build output, so the final deployed artifact is plain
  HTML/CSS/JS with no server runtime required at request time.
* Do NOT create API routes, server actions, middleware, or any backend
  functionality unless a feature explicitly and unavoidably requires it
  (this PRD does not require any such feature). If a chosen library or
  approach would force a non-static/server-rendered deployment, flag it
  and prefer a static-compatible alternative instead.

30. ANTI-AI-SLOP DESIGN RULES
================================================================================

This is a critical requirement. The website must NOT look like a generic
AI-generated portfolio.

Avoid:
* Excessive glassmorphism
* Excessive rounded cards
* Purple-blue gradient backgrounds
* Random glowing blobs
* Generic 3D spheres
* Huge meaningless statistics
* Excessive badges
* "Innovative / Passionate / Creative Developer" filler copy
* Generic SaaS dashboard aesthetic
* Every section inside a card
* Excessive shadows
* Excessive gradients
* Random particles
* Excessive animations
* Stock-photo-looking imagery
* Fake testimonials
* Fake clients
* Fake awards
* Fake experience

Instead:
* Use strong typography
* Use intentional whitespace
* Use visual rhythm
* Use real project structure
* Use restrained color
* Use meaningful interaction
* Use functional demonstrations
* Use editorial composition
* Use subtle imperfections where appropriate
* Make the portfolio feel personally authored

The design should look like a developer with strong product taste built it,
rather than an AI assembling a collection of fashionable UI components.

41. FINAL CREATIVE DIRECTION
================================================================================

The portfolio should communicate: "This person builds things."
Not: "This person downloaded a portfolio template."

The experience should feel like entering a developer's digital workspace.
The visitor should gradually discover:

WHO I AM
   ↓
WHAT I CAN BUILD
   ↓
WHAT I HAVE BUILT
   ↓
WHAT I AM BUILDING
   ↓
HOW TO CONTACT ME

The website should be memorable because of its interaction design, project
demonstrations, typography, composition, and storytelling, not because it
contains the maximum possible number of visual effects.

Build with restraint. Prioritize quality over quantity.

Every visual element must have a purpose.
Every animation must have a reason.
Every section must contribute to the story.
Every project preview should demonstrate actual interaction.

The final result should feel like a premium personal developer portfolio /
interactive digital showcase, not a generic AI-generated landing page.

42. AGENT OPERATING INSTRUCTIONS
================================================================================

These instructions govern HOW the coding agent (Antigravity) should work
through this PRD, independent of the design content above.

1. Never fabricate personal information, project details, statistics, or
   experience that the user has not provided. Use the bracketed placeholder
   format defined throughout this document instead.
2. Never skip ahead to a later phase before the current phase has been
   verified as working.
3. Never rewrite or delete existing working code without a clear,
   stated technical reason.
4. Always check the installed/available skills before implementing a
   feature manually — use a relevant skill if one exists, and do not
   assume one exists if it does not.
5. Always preserve the existing project's framework, folder structure, and
   conventions unless this PRD explicitly requires a change.
6. After each phase, run a self-check: verify the build compiles, check
   the browser console for errors, check responsiveness at desktop/tablet/
   mobile breakpoints, and check that interactive elements actually work.
7. If a requirement in this PRD conflicts with a technical constraint of
   the existing project, flag the conflict and propose the closest
   alternative that preserves the design intent — do not silently ignore
   the requirement.
8. Report progress at the end of each phase before proceeding, using the
   Definition of Done checklist below.

================================================================================
43. DEFINITION OF DONE
================================================================================

A phase is considered complete only when ALL of the following are true:

[ ] All requirements listed for that phase in Section 40 are implemented.
[ ] No console errors on load or during interaction.
[ ] Layout is responsive across desktop, tablet, and mobile.
[ ] All interactive elements (buttons, tabs, filters, modals, nav) respond
    correctly.
[ ] No hardcoded fictional personal data — placeholders are used correctly.
[ ] No "AI slop" visual patterns from Section 30 are present.
[ ] Code is modular and follows the component structure in Section 35.
[ ] Reduced-motion and basic accessibility requirements are respected.
[ ] The phase has been visually reviewed and confirmed before moving to the
    next phase.

The entire project is considered done only when every phase (1–7) meets
