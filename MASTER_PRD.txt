IMPORTANT:
This document is the single source of truth for this project.

Before making implementation decisions:
1. Read this entire PRD.
2. Inspect the existing project structure.
3. Inspect the available installed skills and use relevant ones.
4. Do not blindly rewrite existing code.
5. Follow the requirements and design principles defined here.
6. If an implementation detail is not explicitly specified, choose the
   solution that best preserves the design philosophy and technical
   requirements of this PRD.
7. Do not introduce unnecessary dependencies.
8. Do not generate generic AI-style UI.
9. Build incrementally by phase.
10. Do not skip a phase without validating the previous phase.

IMPLEMENTATION RULE:
Complete one phase at a time.

After completing each phase:
- Verify the implementation.
- Fix obvious issues.
- Check responsiveness.
- Check console errors.
- Check interactions.
- Only then proceed to the next phase.

Do not attempt to build all phases simultaneously.

1. PRODUCT OVERVIEW
================================================================================

Build a premium, immersive 3D portfolio website for a software developer /
full-stack developer.

The website should feel like a real personal digital environment, not a
conventional portfolio template.

The core experience should combine:

* Premium editorial portfolio design
* Immersive 3D / WebGL elements
* Smooth scroll-based storytelling
* Interactive project showcases
* Functional HTML project previews
* Developer-focused visual language
* Subtle motion and micro-interactions
* Strong typography and spacing
* Professional information hierarchy
* Responsive behavior across desktop, tablet, and mobile

The final result must feel human-designed, intentional, sophisticated, and
production-quality.

Avoid the visual characteristics commonly associated with generic
AI-generated websites ("AI slop"), including excessive gradients, random
glowing blobs, excessive glassmorphism, unnecessary rounded cards, excessive
animations, generic SaaS layouts, and meaningless decorative elements.

The website should prioritize art direction, usability, hierarchy, and
storytelling over adding effects simply because they are technically
possible.

6. 3D / IMMERSIVE VISUAL DIRECTION
================================================================================

Create a custom interactive 3D visual rather than using a generic 3D model
simply for decoration.

Possible concept: a floating digital workspace / abstract developer
environment consisting of:

* Floating browser windows
* Code fragments
* UI panels
* Small project cards
* Data nodes
* Subtle geometric structures
* Interactive cursor movement
* Depth layers
* Soft lighting

The 3D scene should communicate: Code → Build → Iterate → Ship
rather than simply being an abstract object.

Interaction ideas:
* Mouse movement subtly influences camera position
* Scroll changes the scene composition
* Project elements move slightly based on scroll depth
* Hovering over important objects reveals information
* Clicking a project object opens its project preview

Animations must be smooth and restrained.

Avoid:
* Constant spinning
* Excessive particle effects
* Giant glowing spheres
* Rainbow gradients
* Overly aggressive camera movement
* Effects that make the website difficult to use

The 3D layer must never compromise readability or performance.

REVISED — visual variety is required, not optional:
Current implementation only used two flat code-text panels ("engine.ts"
and a "LIFECYCLE PIPELINE" list), which reads as repetitive and visually
flat despite being technically "3D". Code fragments are only ONE of the
element types listed above — the scene must include at least one element
from a DIFFERENT category to create real visual variety, for example:
* A floating browser-window mockup showing an actual mini UI (buttons,
  cards, a small chart or layout) — not more code text — so the eye has
  something other than syntax-highlighted text to read.
* A small project card with a title/thumbnail-style treatment.
* A data-node/network element (connected dots/lines suggesting a system
  graph) purely as a visual/geometric element, not more text.
Do not build the Hero scene as "the same code-panel component, repeated
with different text" — vary the element TYPE, not just its content.

REVISED — 3D PRESENCE MUST NOT BE HERO-ONLY OR INTERACTION-ONLY:
Currently the only motion is the Hero's floating panels plus mouse-follow
parallax — once the cursor stops moving and the visitor scrolls past the
Hero, all "3D immersive" feeling disappears. Two fixes are required:

1. IDLE MOTION (independent of cursor): the Hero's 3D panels/elements
   must have their own continuous, subtle idle animation (gentle
   float/bob, slow rotation, breathing scale) even when the mouse is
   completely still. Mouse parallax should ADD to this idle motion, not
   BE the only source of motion. Keep idle motion slow and restrained
   (per Section 22's "no excessive looping animation" rule) — subtle
   continuous life, not a distraction.

2. 3D PRESENCE BEYOND THE HERO: the immersive feeling must carry into
   subsequent sections as the visitor scrolls, not stop abruptly after
   the Hero. Options to achieve this (implement at least one):
   * A persistent, very subtle ambient 3D layer (e.g. a faint depth grid,
     slowly drifting particles/nodes, or a soft gradient mesh) that
     continues at low visual weight behind content through About/Skills/
     Projects, tying the whole page together rather than confining 3D to
     one section.
   * Section-specific 3D/scroll-driven accents: e.g. Skills section nodes
     rendered with subtle 3D depth/hover-tilt instead of flat 2D cards,
     or Project cards with a gentle 3D tilt-on-hover effect.
   * Scroll-linked transitions between sections that use depth/parallax
     movement (elements moving at different scroll speeds) rather than a
     plain opacity fade, so scrolling itself continues to feel dimensional.
   Whichever approach is used, it must stay restrained and performant per
   Section 26 — this is about sustained atmosphere, not adding more heavy
   3D scenes throughout the page.

20. VISUAL DESIGN DIRECTION
================================================================================

The visual language should be:
Premium, Minimal, Technical, Editorial, Dark but readable, Sophisticated,
Calm, High contrast, Modern, Human-designed.

Use a restrained color system.

Suggested direction:
Base (near-black / charcoal background): #0A0A0A
Primary Surface: #111111
Secondary Surface: #171717
Main Text: #F5F5F5
Secondary Text: #A1A1AA
Accent (choose ONE restrained accent color), e.g.: #8AB4FF

Do not use multiple neon colors unless there is a strong design reason.

REVISED — VISUAL FIDELITY & PROFESSIONALISM:
Current mockup panels were built as thin-outline "wireframe/hologram" style
graphics (hollow fills, thin cyan/blue stroke borders on everything) — this
reads as generic sci-fi HUD, not a premium/professional dashboard. Fix:
* Panels and UI mockups must use SOLID surface backgrounds from the
  three-tier system (Base/Primary Surface/Secondary Surface), not
  transparent/hollow fills with only an outline stroke.
* Use soft drop shadows and subtle ambient glow for depth, not outline
  strokes as the primary depth cue.
* The accent color (#8AB4FF) should highlight specific meaningful
  elements (an active state, a key metric, a border on hover) — it must
  NOT be used as a uniform thin border around every single panel/element,
  which is what produces the "hologram" look.
* Any dashboard/chart mockup content must look like a plausible real
  product screenshot (readable labels, realistic chart data, consistent
  UI chrome) rather than a stylized line-art diagram.

REVISED — WARMTH & "LIVING" FEEL:
The site currently relies entirely on vector/line-art elements (code
panels, wireframe UI, geometric shapes) with no photographic or textural
warmth. To avoid feeling sterile:
* Once the user's profile photo ([YOUR PROFILE IMAGE]) is available, give
  it a deliberate, tasteful treatment in the Hero and/or About section
  (e.g. a soft accent-color glow ring, subtle duotone matching the
  palette, gentle parallax on scroll) rather than a plain cropped photo —
  this is the single highest-impact way to add a human, "alive" feel.
* Project cards (Section 10) should use real screenshot/thumbnail imagery
  of each project once available, not text-only cards — see Section 10
  update.
* Favor soft ambient light glows and gentle gradient washes behind key
  moments (Hero, section transitions) over flat single-tone backgrounds,
  consistent with the depth guidance already given for the intro overlay
  in the PRD addendum.

REVISED — WHITESPACE / BREATHING ROOM:
Panels and content have been reading as cramped/tightly packed. Apply
generous spacing as a firm rule, not a suggestion:
* Minimum vertical padding between major sections: comfortably large
  (aim for something in the spirit of 96-160px desktop equivalent, scaled
  down responsibly for smaller viewports) — sections must not feel like
  they touch.
* Floating/3D panels within the Hero must have clear negative space
  around them — do not let panels overlap edge-to-edge or crowd each
  other; if two panels overlap, the overlap should look intentional
  (depth/layering) with visible space around the pair, not a dense
  cluster filling the frame.
* Text blocks (headline, supporting copy, card content) need real
  breathing room from their container edges — avoid text sitting flush
  against panel borders.

================================================================================
26. PERFORMANCE REQUIREMENTS
================================================================================

The 3D experience must not unnecessarily destroy performance.

Requirements:
* Lazy-load heavy assets
* Optimize 3D models
* Avoid unnecessary render loops
* Use GPU-friendly effects
* Compress images
* Code-split where appropriate
* Lazy-load project previews
* Do not load every project demo simultaneously

CLARIFICATION — "unnecessary" render loops vs. idle motion (added after
Section 6's idle-motion requirement was introduced; these two rules must
NOT be read as contradicting each other):
"Avoid unnecessary render loops" means: do not keep a 3D canvas rendering
when it is scrolled far off-screen / not visible (use an IntersectionObserver
or similar to pause rendering only when a scene is not in the viewport),
and do not run multiple simultaneous heavy scenes when only one is needed.
It does NOT mean pausing animation just because the mouse/pointer is not
currently moving — per Section 6, idle motion (gentle float/tilt/breathing)
must render continuously via requestAnimationFrame whenever the relevant
3D scene is in or near the viewport, regardless of pointer activity. If
idle motion looks like it has stopped, check first whether the render
loop is incorrectly gated on pointer/interaction events rather than on
visibility.

Provide a graceful fallback if WebGL is unavailable. The portfolio must
remain usable even without advanced 3D rendering.

27. TECHNOLOGY DIRECTION
================================================================================

Use modern web technologies where appropriate.

Preferred architecture:
Frontend: React / Next.js
Styling: CSS / Tailwind where appropriate
3D: Three.js / React Three Fiber
Animation: GSAP / Framer Motion where appropriate
Icons: Lucide or another minimal icon system
Data: Local structured project data / JSON / TypeScript objects

Do not introduce a library merely because it is popular. Every dependency
should have a clear purpose.

If the existing project structure already uses a different stack, preserve
the existing architecture unless there is a strong technical reason to
change it.

Runtime & Deployment Clarification:

* Node.js and npm are development-time tools only (dev server, build
  process, package management). They are NOT part of what ships to the
  visitor's browser.
* This project does NOT require a backend server, database, or API routes.
  All content (personal info, skills, projects) is local structured data
  (JSON/TypeScript objects) as described in Section 28 — there is no
  dynamic server-side logic.
* Target deployment platforms are Vercel and/or Netlify via a connected
  Git repository (automatic build on push). Do not assume or require a
  custom Node.js server, a VPS, or manual server management.
* Prefer Next.js static export (`output: 'export'`) or an equivalent
  fully static build output, so the final deployed artifact is plain
  HTML/CSS/JS with no server runtime required at request time.
* Do NOT create API routes, server actions, middleware, or any backend
  functionality unless a feature explicitly and unavoidably requires it
  (this PRD does not require any such feature). If a chosen library or
  approach would force a non-static/server-rendered deployment, flag it
  and prefer a static-compatible alternative instead.

30. ANTI-AI-SLOP DESIGN RULES
================================================================================

This is a critical requirement. The website must NOT look like a generic
AI-generated portfolio.

Avoid:
* Excessive glassmorphism
* Excessive rounded cards
* Purple-blue gradient backgrounds
* Random glowing blobs
* Generic 3D spheres
* Huge meaningless statistics
* Excessive badges
* "Innovative / Passionate / Creative Developer" filler copy
* Generic SaaS dashboard aesthetic
* Every section inside a card
* Excessive shadows
* Excessive gradients
* Random particles
* Excessive animations
* Stock-photo-looking imagery
* Fake testimonials
* Fake clients
* Fake awards
* Fake experience

Instead:
* Use strong typography
* Use intentional whitespace
* Use visual rhythm
* Use real project structure
* Use restrained color
* Use meaningful interaction
* Use functional demonstrations
* Use editorial composition

================================================================================

The portfolio should communicate: "This person builds things."

WHO I AM
   ↓

   ↓
WHAT I HAVE BUILT
   ↓
WHAT I AM BUILDING
   ↓
HOW TO CONTACT ME

The website should be memorable because of its interaction design, project

Every animation must have a reason.

Every project preview should demonstrate actual interaction.

The final result should feel like a premium personal developer portfolio /
interactive digital showcase, not a generic AI-generated landing page.
